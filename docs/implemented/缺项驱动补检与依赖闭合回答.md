## 已接入的闭环

1. [query_plan.py](../../memoria/memory/evidence/query_plan.py)先仅从问题和既有解析结果生成冻结需求，保留主体、条件、否定、事实/记录时间与未知项。当前有限规则可分解“哪个项目、采用什么、选择原因、后续问题”四类需求；其他问题保留完整原问题的总体需求。它不是通用、多语言任意多跳规划器，尚未单独引入付费 LLM Planner。
2. 个人入口复用原 Keyword/BM25/Dense/RRF、可选实体召回、经历和 Claim/时间路由。资料入口复用原资料词面检索、巩固卡与可选实体补召，没有将资料库词面检索宣传为个人 Dense/RRF。每轮实际候选、原排序/分数、拒绝原因及依赖留在当前账号的返回和运行记录中。
3. 模型只检查至多16个完整候选单元、16000字符的引用目录。必须逐项复制全部冻结需求，不能删除缺失的一跳；supported 必须有本轮真实原话，conflict 需要两个不同来源，Span/SHA、身份与当前来源依赖由程序检查。完整主语、条件与事实需要原话支持；词面相关或高自信不是充分性。
4. `initially_recalled_but_not_selected` 标记原选择遗漏的必要候选；`not_supported_in_assessed_pool` 标记模型在**已检查池内**仍找不到支持的需求。`omitted_from_gate` 单列模型池上限造成的未检查项，不能将它们宣称为整个记忆库没有该证据。
5. 只有缺项时执行**一轮、最多两条短查询**补检。仅替换检索定位词，原始问题、账号、会话、主体、实体身份核验、适用条件和事实/记录时间仍使用同一请求，不能让模型查询改变访问范围。空的首次召回也可按问题需求补检一次；来源无法完整放入检查池、真实冲突或必要组预算不足，不通过读完整历史解决。
6. 补检后重新检查完整需求，仍缺项即停止；冲突澄清，没有可信支持则拒答。[closure.py](../../memoria/memory/evidence/closure.py)按原话引用映射到完整候选组，递归闭合显式依赖，保留名称对应、事实、条件和完整支持组。必要组放不进相同证据预算/数量上限时不截成半组；这属于选择预算缺口，不报告成召回缺失。
7. Reader 只能引用最终完整呈现的目录，回答必须保留全部必要引用，再经过独立支持核验。发布前再次检查来源、角色/主体依赖、记忆版本、Observation语义、条件、撤回和待审状态提案。模型的 Supported 仍是有原话约束的建议，不代表现实核验或正确率标签。

“之前、当时、后来”可表示叙事关联，无明确日期时保留未知，不强迫转换ISO时间戳；具体日期范围仍走既有时间过滤。普通事件的时间不确定性不能用上传时间补齐。资料Reader按明确事实范围过滤；记录时间的区间知识状态重建仍保守澄清，不宣称已重建任意过去的完整数据库。

## 生产调用与开关

`QueryRequest` 和 `KnowledgeAnswer` 新增 `use_adaptive_retrieval`：

- `null`（默认）：Kernel对命中至少两类上述需求的问题自动使用闭环；显式开启独立查询模型/重排时不自动叠加。
- `true`：显式启用；与 `use_query_model` / `use_llm_rerank` 同时要求时返回422，避免分离的预算器重复花费。
- `false`：保持原读取/选择/Reader，用于有限规则基线和后续消融。

例如个人读取：

```json
{"query":"我之前在哪个项目采用了快照方案？当时为什么选择它？后来遇到了什么问题？","use_adaptive_retrieval":true,"budget_chars":16000,"candidate_limit":32,"top_k":8}
```

发送到 `POST /api/memory-answer`。资料使用同一问题、开关及 `budget_chars`，发送到 `POST /api/memory-kernel/knowledge-answer`，仅接受library域。

Chat/飞书/QQ/Telegram共用运行时对明确回忆过去、且命中多项需求的问题调用同一Kernel闭环，最终文本缓冲到核验后发布；维持正常生命周期、记忆任务入队和账号隔离。普通建议、症状原因等不因提到个人事实槽位而被误路由。Chat的AFTER_REASONING钩子改写答案、或在读取后撤回来源，均不能直接发布原结论。简单状态查询和一般对话保留原流程。

## 同一总预算

单次回答最多8次模型请求、完整累计输入240000 UTF-8字节；两次覆盖检查各至多一次格式修复，Reader最多两次（仅格式/长度失败完整重生成一次）、支持核验至多两次。HTTP Embedding（若使用）同样占用这8次和累计字节，不能另开免费调用额度；本地进程BGE只记录检索/Embedding耗时，不伪装成远程付费Token。

每次覆盖检查前预留完整Reader及一次格式重生成、最坏4000字符答案和两次支持核验；最终证据选择后再次核算真实完整请求。预留不足即停止。完整有界候选池用于保守预留，可能因过大而停止，不能承诺任何池都能自动缩成足够答案。所有模型输出也按当前Reader模型、窗口和输出空间检查；字符/字节上限不是远程模型精确Token，实际Token使用provider usage，缺失单列未知。

自适应请求通过任务局部ContextVar禁用HTTP隐式重试，不修改共享模型配置；JSON修复是预算内显式调用。LLM原始返回、格式/长度失败、Embedding usage/失败、请求预算、阶段耗时和未知计数留在 `adaptive.calls`，Reader usage单列，聚合时不能再次重复累加。外层模型提供方的不可观测服务内部重试不作可测量调用数。

每次模型调用及每次检索使用不超过配置值且最多90秒的墙钟上限，不依赖HTTP读超时能否被keepalive重置；超时不无限重发，释放未使用的Reader预留，未知用量保留。凭据检查覆盖原问题和完整未来Reader消息，包括标题、身份及其他元数据，不仅检查正文原话。
