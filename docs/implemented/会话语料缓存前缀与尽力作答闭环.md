# 会话语料缓存前缀与尽力作答闭环

2026-10-24。用户基于DeepSeek控制台（实测时段命中99.4万/未命中320.7万，≈23.7%）与首轮全量逐题记录提出两件事并按序授权：先把Memoria组的provider缓存命中率做到实测80%以上，再核查首轮全量605条普通题错误拒答与366条执行失败并做到"全部给出答案、最多判错"，最后以新协议全量复测并更新README、中间结果不推远程。

## 一、会话语料稳定前缀（缓存命中率）

诊断：Baseline同一会话每题复用整段历史前缀，命中98.57%；Memoria各阶段（Gate/Reader/支持/补检）证据数组互不相同、跨题只有固定System稳定，36题实测整体命中仅20–24%，与控制台一致。

实现（[deepseek_cache.py](../../memoria/llm/deepseek_cache.py)、[adaptive_retrieval.py](../../memoria/memory/adaptive_retrieval.py)）：每个会话的全部活跃来源行（单元+原始窗口，按revision/start/end确定性排序）序列化为一个字节稳定的围栏语料块，缓存在Kernel上；仅官方DeepSeek端点在**客户端发送层**把 `[固定System, 语料块]` 前缀注入该会话的每一次分阶段调用。语料块每会话首次冷写一次，其后全部调用命中复用；预算计量仍只针对变量区（语料前缀按命中价摊销，单会话一次付费）。引用资格不变：每阶段仍只允许其呈现证据与allowlist，语料可见性永不构成可引用性；语料为不可信数据并带"仅任务参数列出的ID可用"的声明。工程测试模型非官方端点，不注入，全部旧测试不受影响。

36题冻结输入实测：**整体Token加权命中率84.57%（上轮21–24%），其中answer+support阶段90.84%**；Judge 61.8%；形成阶段27.2%（窗口内容各自唯一、一次性处理，属结构性低命中，占费用比例小）。

## 仍需验证

best-effort与support-override把部分错误拒答转为答案的同时也引入少量答错（36题上2–4例），属"最多判错"政策的预期代价；对抗题依赖Reader自身拒答保持正确拒答，全量对抗分数是该安全边界的主要检验。语料前缀使模型可见全会话原文，引用资格仍由程序校验约束，但其对Gate判定质量的长期影响需全量逐类分数复核。形成准入（2407条主体绑定）未在本轮处理，多跳/计数类收益仍待形成层修复。
